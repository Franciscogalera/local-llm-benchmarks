## 2. Installation — die drei Fallstricke

### 2.1 Ubuntus `nvidia-cuda-toolkit` ist unbrauchbar

```
apt-cache policy nvidia-cuda-toolkit  →  Candidate: 12.4.131
```

**CUDA 12.4 kennt `sm_120` nicht.** Blackwell braucht mindestens **12.8**.
Ein Build damit bricht mit `Unsupported gpu architecture 'compute_120'` ab.
Also NVIDIAs eigenes Repo verwenden:

```bash
cd /tmp
wget https://developer.download.nvidia.com/compute/cuda/repos/ubuntu2604/x86_64/cuda-keyring_1.1-1_all.deb
sudo dpkg -i cuda-keyring_1.1-1_all.deb
sudo apt update
```

Für Ubuntu 26.04 („resolute") gibt es ein natives `ubuntu2604`-Repo.
(`ubuntu2504` existiert nicht, `ubuntu2404` wäre die Ausweichvariante.)

### 2.2 Niemals das Metapaket `cuda` installieren

```bash
sudo apt install cuda-toolkit-13-3      # richtig
sudo apt install cuda                   # FALSCH
```

Das Metapaket `cuda` hängt an `cuda-drivers` (Kandidat **610.43.02**) und würde
den laufenden 595er-Treiber mitsamt Kernelmodul ersetzen. `cuda-toolkit-13-3`
zieht ausschließlich Compiler und Bibliotheken.

Vor jeder Installation prüfen:

```bash
sudo apt install --dry-run cuda-toolkit-13-3 | grep -E '^Remv|595|nvidia-driver'
```

Muss leer bleiben. Ergebnis hier: 75 Pakete, 3173 MB Download, 6367 MB auf
Platte, **`Removing: 0`**.

Kein APT-Pinning nötig: `apt upgrade` ersetzt nur Pakete *gleichen Namens*, und
`nvidia-driver-610-open` ist ein anderer Paketname als `nvidia-driver-595-open`.
Aus NVIDIAs Repo wollte nur `nvidia-settings` (510 → 610) hoch — ein reines
GUI-Werkzeug ohne Treiberabhängigkeiten.

### 2.3 `LD_LIBRARY_PATH` wird **nicht** gebraucht

Fast jede Anleitung im Netz behauptet das Gegenteil. Es stammt aus der Zeit der
`.run`-Installer. Die `.deb`-Pakete registrieren sich selbst:

```
/etc/ld.so.conf.d/000_cuda.conf   →  /usr/local/cuda/targets/x86_64-linux/lib
/etc/ld.so.conf.d/987_cuda-13.conf
```

`ldconfig -p` findet `libcublas.so.13` und `libcudart.so.13` daraufhin von
allein. `LD_LIBRARY_PATH` wäre sogar schädlich, weil es an jeden Kindprozess
vererbt wird und dort Vorrang vor den Systempfaden hat.

Nötig ist nur der `PATH` (steht in `~/.bashrc`, Zeile 118):

```bash
export PATH=/usr/local/cuda/bin:$PATH
```

`/usr/local/cuda` ist ein Symlink über `/etc/alternatives/cuda` auf
`/usr/local/cuda-13.3` — bei einem späteren CUDA 14 biegt man nur den Link um.

### 2.4 GCC-Version

```
/usr/local/cuda/targets/x86_64-linux/include/crt/host_config.h:
    #if __GNUC__ > 15
```

CUDA 13.3 akzeptiert **bis einschließlich GCC 15**. Installiert ist 15.2.0 —
passt gerade noch. Bei GCC 16 wäre
`-DCMAKE_CUDA_HOST_COMPILER=/usr/bin/g++-15` nötig.


## 5. Ergebnisse

Alle CPU-Werte zum Vergleich stammen aus dem Lauf vom 25.07. (12 Threads).

### 5.1 Bonsai-27B Q1_0 — das einzige Modell, das komplett ins VRAM passt

`llama-bench -ngl 99`, Standardkontext (640 Token):

| | CPU | RTX 5070 Ti | Faktor |
|---|---:|---:|---:|
| pp512 | 14,0 t/s | **2014,3 ± 95,9 t/s** | **144×** |
| tg128 | 8,7 t/s | **102,9 ± 0,4 t/s** | **11,8×** |

Der tg-Faktor liegt **über** dem Bandbreitenverhältnis (896/70 ≈ 12,8, praktisch
eher 9). Grund: Bonsai Q1_0 war auf der CPU laut Analyse vom 25.07.
**rechenlimitiert** (nur 33 GB/s genutzt), nicht bandbreitenlimitiert. Solche
Modelle gewinnen beim Umzug auf die GPU doppelt.

Auch auf der GPU bleibt es rechenlimitiert: 3,79 GB × 102,9 t/s ≈ **390 GB/s**
von 896 GB/s, also nur **44 % Bandbreitenausnutzung**. Bei 1 Bit pro Gewicht
steckt zu viel Entpack- und Rechenarbeit in jedem gelesenen Byte.

### 5.2 Qwen3.6-27B Q4_K_M — passt nicht, Layer-Sweep

Modell 16,74 GiB gegen 15,5 GiB nutzbares VRAM. `llama-bench`, Standardkontext,
FP16-Cache:

| `-ngl` | pp512 | tg128 | ms/Token |
|---:|---:|---:|---:|
| 40 | 733,95 | 8,96 | 111,6 |
| 48 | 884,46 | 11,81 | 84,7 |
| 54 | 1066,41 | 15,29 | 65,4 |
| 58 | 1202,36 | 19,08 | 52,4 |
| 60 | \- | **`failed to create context`** | \- |

**Kernbefund: Jeder auf die GPU verschobene Layer spart konstant ~3,25 ms.**
Der Durchsatz sieht überproportional aus, aber in Zeit gerechnet ist es exakt
linear (Amdahl). Gegenprobe: ein Layer ist 16,74 GiB ÷ 65 = 0,277 GB, bei den
gemessenen ~70 GB/s RAM-Bandbreite also 3,95 ms; derselbe Layer kostet auf der
GPU bei 896 GB/s rund 0,3 ms. Differenz **3,65 ms** gegen **3,25 ms** gemessen —
die CPU-Layer laufen also nachweislich an der RAM-Bandbreitengrenze.

**Warum 60 scheitert:** Die Meldung lautet `failed to create context`, nicht
`failed to load model`. Die Gewichte passten noch.

| | Gewichte | Rest von 15,5 GiB |
|---|---:|---:|
| `-ngl 58` ✅ | 14,94 GiB | 0,56 GiB für KV + Compute-Buffer |
| `-ngl 60` ❌ | 15,46 GiB | 0,04 GiB — unmöglich |

Mit quantisiertem Cache geht ein Layer mehr:

```bash
llama-bench -ngl 59 -ctk q8_0 -ctv q8_0 -fa 1   →   pp 1198,9 | tg 20,21
```

`-fa 1` ist dabei **Voraussetzung**, nicht Kür: Nur der Flash-Attention-Kernel
rechnet direkt auf einem quantisierten V-Cache.

> **Achtung, `llama-bench` bricht die gesamte Sweep-Liste beim ersten
> Fehlschlag ab** statt die Konfiguration zu überspringen. Immer von unten
> herantasten.

### 5.3 Kontext frisst Layer

Pro Token und Layer: (256 + 256) × 4 Köpfe = 2048 Werte → **4096 Byte in FP16**,
über 65 Layer **260 KiB pro Token**.

| Kontext | KV FP16 | KV q8_0 |
|---:|---:|---:|
| 640 (llama-bench-Standard) | 0,16 GiB | 0,08 GiB |
| 8 192 | 2,03 GiB | 1,02 GiB |
| 32 768 | 8,13 GiB | **4,06 GiB** |
| 65 536 | 16,25 GiB | 8,13 GiB |
| 131 072 | 32,50 GiB | 16,25 GiB |

Umgerechnet aufs Layer-Budget (q8_0-Cache, 0,258 GiB Gewichte je Layer):

| Kontext | KV je Layer | Kosten je Layer | Layer auf GPU |
|---:|---:|---:|---:|
| 8 192 | 0,016 GiB | 0,274 GiB | ~56 |
| 32 768 | 0,063 GiB | 0,320 GiB | ~48 |
| 65 536 | 0,125 GiB | 0,383 GiB | ~40 |
| 131 072 | 0,250 GiB | 0,508 GiB | ~30 |

**`-ctk/-ctv q8_0` ist bei 32k acht zusätzliche Layer wert** — kein Feinschliff,
sondern der Hebel.

Gemessen mit `llama-bench -d 8192 -ctk q8_0 -ctv q8_0 -fa 1`:

| `-ngl` | pp512 @ d8192 | tg128 @ d8192 | ms/Token | Ersparnis je Layer |
|---:|---:|---:|---:|---:|
| 48 | 858,13 | 9,72 | 102,9 | |
| 52 | 932,49 | 11,73 | 85,3 | 4,40 ms |
| 55 | 1029,55 | 13,97 | 71,6 | 4,57 ms |

Wieder linear — aber der Layer-Preis steigt von **3,25 ms** (640 Token) auf
**~4,5 ms** (8192 Token), weil jeder CPU-Layer zusätzlich seinen Anteil am
KV-Cache durchgehen und die q8_0-Werte entpacken muss.

Von 640 auf 8192 Token kostet das **31 % Generierungsgeschwindigkeit**
(20,21 → 13,97 t/s).

### 5.4 MTP — Multi-Token Prediction

**Beide Qwen3.6-Modelle bringen einen trainierten MTP-Kopf mit**, und llama.cpp
unterstützt ihn für `qwen35` / `qwen35moe`:

```
qwen35.nextn_predict_layers = 1
blk.64.nextn.eh_proj.weight, .enorm, .hnorm, .shared_head_norm
```

Der Kopf rät *n* Token voraus, das Hauptmodell prüft sie in **einem** Durchlauf.
Weil `tg` bandbreitenlimitiert ist, kostet die Prüfung von 4 Token fast dasselbe
wie von einem. **Das Ergebnis ist Token für Token identisch** — verworfene
Entwürfe werden verworfen, es kommt nie ein anderes Token heraus.

Kein zweites Modell nötig, der Kopf sitzt in derselben Datei und teilt sich den
KV-Cache.

`llama-cli -ngl 55 -c 8192 -ctk q8_0 -ctv q8_0 -fa 1 -st --seed 42 -n 200`:

| `--spec-type` | Prompt | Generation |
|---|---:|---:|
| `none` | 45,6 t/s | 15,9 t/s |
| `draft-mtp` | 42,1 t/s | **31,0 t/s** — **+95 %** |

Entwurfstiefe `--spec-draft-n-max`:

| n-max | 2 | **3 (Standard)** | 4 | 6 |
|---|---:|---:|---:|---:|
| Generation | 29,7 | **31,0** | 30,3 | 26,5 t/s |

**Der Standardwert 3 ist optimal.** Aus dem Faktor ~2 lässt sich die
Trefferquote zurückrechnen: Bei sequentieller Annahme (Abbruch beim ersten
Fehler) ergibt `p + p² + p³` plus das garantierte Token rund 2,2 Token pro
Durchlauf → **p ≈ 0,6**, also 60 % Trefferquote. Genau der typische Wert für
einen mittrainierten Kopf.

Der Prompt-Verlust von 7,7 % ist die Kehrseite: Beim Prefill läuft der MTP-Kopf
mit, bringt dort aber nichts, weil ohnehin alle Token parallel verarbeitet
werden. Guter Tausch.

Dauerhaft aktivieren:

```bash
export LLAMA_ARG_SPEC_TYPE=draft-mtp
```

Wirkt auf `llama-cli` und `llama-server`; Modelle ohne MTP-Kopf ignorieren es.
`llama-bench` unterstützt spekulatives Dekodieren **nicht**.

### 5.5 MoE gegen dicht — die eigentliche Entscheidung

`llama-cli -ngl 99 -c 8192 -ctk q8_0 -ctv q8_0 -fa 1 --spec-type draft-mtp -st --seed 42 -n 200`:

| `--n-cpu-moe` | Prompt | Generation |
|---:|---:|---:|
| 10 | 117,4 t/s | **113,5 t/s** |
| 15 | 106,5 t/s | 111,2 t/s |
| 20 | 106,3 t/s | 106,5 t/s |

Weniger CPU-Experten = schneller, monoton. **10 ist der bisher beste getestete
Wert**, niedrigere wurden noch nicht probiert.

Direktvergleich bei identischen Einstellungen:

| Modell | Generation | |
|---|---:|---:|
| Qwen3.6-27B Q4_K_M (dicht), `-ngl 55` | 31,0 t/s | |
| **Qwen3.6-35B-A3B Q4_K_M (MoE)**, `--n-cpu-moe 10` | **113,5 t/s** | **3,7×** |

`--n-cpu-moe N` lässt die Experten-Tensoren der ersten N Layer im RAM und
schiebt alles andere auf die GPU. Das ist beim MoE der richtige Hebel statt
`-ngl`: Von 35,5 Mrd. Parametern sind pro Token nur ~3 Mrd. aktiv, die selten
gebrauchten Experten dürfen also im langsamen Speicher liegen, während
Attention und KV-Cache — der bei langem Kontext dominierende Posten —
vollständig auf der GPU bleiben.

### 5.6 Praxislauf — dichtes 27B bei 32k Kontext

Erste echte Arbeitslast statt synthetischem Benchmark: Prompt „baue ein
Auto-Rennspiel", vollständige Code-Generierung bis zum Ende (`-n -1`).

```bash
./build-cuda/bin/llama-cli -m ~/models/Qwen_Qwen3.6-27B-Q4_K_M.gguf \
  -ngl 48 -c 32768 -ctk q8_0 -ctv q8_0 -fa 1 --spec-type draft-mtp -n -1
```

| | |
|---|---:|
| Prompt | 24,3 t/s |
| Generation | **22,7 t/s** |

`-ngl 48` statt 55, weil bei 32k Kontext ein Layer 0,32 GiB statt 0,27 GiB
kostet (siehe 5.3). Die Vorhersage aus dem Layer-Modell lautete 20–25 t/s —
**gemessen 22,7 t/s**, das Modell aus Abschnitt 5.2/5.3 trägt also auch unter
realer Last.

> **Häufiger Fehler:** `-n 200` (der Standard aus den Benchmark-Aufrufen)
> schneidet lange Antworten mitten im Code ab. Für echte Arbeit `-n -1`.

| Qwen3.6-35B-A3B Q4_K_M (MoE) | 20,5 t/s | 113,5 t/s | **5,5×** |

Das Ranking vom 25.07. bleibt bestehen und verschärft sich sogar: **Das MoE ist
und bleibt das mit Abstand schnellste Modell auf dieser Maschine.** Das dichte
27B holt durch MTP zwar deutlich auf (Faktor 8 statt 5,5), landet aber immer
noch bei einem Viertel der MoE-Geschwindigkeit.

**Aber: Geschwindigkeit ist nicht Qualität.** Beim Praxislauf (5.6, Prompt
„baue ein Auto-Rennspiel") lieferte das **dichte 27B das subjektiv bessere

plausibel: Beim MoE sind pro Token nur ~3 von 35,5 Mrd. Parametern aktiv, beim
dichten Modell alle 27,3 Mrd.

**Daumenregel: MoE für Durchsatz und lange Kontexte, dichtes 27B wenn die
Ausgabequalität zählt.** Bislang nur subjektiv verglichen, ein systematischer
Qualitätsvergleich steht aus.

## 7. Wichtige Einschränkung dieser Messreihe

**Die `llama-cli`-Werte aus 5.4 und 5.5 gelten für kurzen Kontext, nicht für
8192 Token.** `-c 8192` legt nur den Cache *an*; der Prompt war rund 20 Token
lang, während der Generierung standen also nur ~250 Token im Cache. Nur die
`llama-bench`-Werte mit `-d 8192` (Abschnitt 5.3) sind echte 8k-Messungen.

Die MTP- und MoE-Zahlen sind damit **untereinander** sauber vergleichbar
(identische Bedingungen), aber sie überzeichnen den Alltag mit gefülltem

## 8. Maximaler Kontext beim dichten 27B — Hochrechnung

> **Alle Zahlen dieses Abschnitts sind gerechnet, nicht gemessen.**

Grundwerte: Gewichte 16,74 GiB (17143 MiB), 65 Layer à 0,258 GiB.
KV-Cache pro Token über alle 65 Layer:

| Cache-Typ | je Token | je Layer und Token |
|---|---:|---:|
| FP16 | 260 KiB | 4096 B |
| q8_0 | 130 KiB | 2048 B |
| q4_0 | ~73 KiB | ~1152 B |

### 8.1 Eine Karte (15841 MiB nutzbar)

Das Modellmaximum von 262.144 Token ist erreichbar, aber nur mit `q4_0` und
wenigen Layern auf der GPU:

| Kontext | Cache | Layer auf GPU | geschätzt |
|---:|---|---:|---|
| 131.072 | q4_0 | ~40 | ~8–10 t/s |
| 262.144 | q4_0 | ~30 | ~5–6 t/s |

`q4_0` im KV-Cache kostet bei langen Kontexten spürbar Qualität — `q8_0` ist der
sicherere Kompromiss und erlaubt auf einer Karte etwa 130k.

### 8.2 Zwei Karten (31682 MiB = 30,94 GiB nutzbar)

Frei für den KV-Cache nach Abzug von Gewichten und ~1000 MiB Compute-Buffern:
**13539 MiB**.

| Kontext | Cache | Layer auf GPU | mit MTP geschätzt |
|---:|---|---:|---:|
| 105.000 | q8_0 | **alle 65** | ~50–55 t/s |
| 190.000 | q4_0 | **alle 65** | ~45–50 t/s |
| 262.144 (Maximum) | q4_0 | 54 von 65 | ~12–15 t/s |

**Der Knick liegt zwischen 190k und 262k.** Bis ~190k passt alles auf die
Karten. Für die vollen 262k müssen 11 Layer zurück auf die CPU — und bei dieser
Kontextlänge kostet ein CPU-Layer nicht mehr 4,5 ms, sondern über 8 ms, weil
zusätzlich ~300 MB KV-Cache aus dem RAM gelesen werden müssen.

Die vollen 262.144 Token vollständig im VRAM gehen auch mit zwei Karten nicht:
262.144 × 73 KiB = 18,7 GiB Cache plus 16,74 GiB Gewichte = 35,4 GiB gegen
30,94 GiB verfügbar.

**Empfehlung: 190k mit q4_0 oder 105k mit q8_0 (bessere Qualität), beides bei
~50 t/s. Die letzten 70k Kontext kosten drei Viertel der Geschwindigkeit.**

### 8.3 Geschwindigkeit bei voller GPU-Auslagerung (eine Karte, kurzer Kontext)

Gemessen wurden 31,0 t/s mit MTP bei `-ngl 55`, also 10 Layern auf der CPU.
Ohne MTP waren es 15,9 t/s = 62,9 ms/Token. Lägen alle 65 Layer auf der GPU,
entfielen 10 × 3,25 ms → 30,4 ms → **~33 t/s ohne MTP**, mit MTP (Faktor 1,95)
**~60–65 t/s**. Das gilt allerdings nur bei kurzem Kontext; bei 100k+ wird die
Attention selbst zum Hauptposten und die Trefferquote des MTP-Kopfs sinkt
erfahrungsgemäß.
