## 3. Die Grundlagen — was gemessen wird

**`pp512` = Prompt Processing.** 512 Tokens auf einmal verarbeiten. Alle Tokens
werden gleichzeitig durchgeschoben, die Gewichte einmal geladen und für alle
benutzt → **rechenlimitiert**. Praktisch: wie schnell ein Prompt eingelesen wird.

**`tg128` = Text Generation.** 128 Tokens einzeln erzeugen. Jedes Token hängt vom
vorigen ab, also muss für *jedes einzelne* Token wieder gelesen werden →
**bandbreitenlimitiert**. Praktisch: wie schnell es „tippt".

**MoE (Mixture of Experts).** Qwen3.6-35B-**A3B** hat 35 Mrd. Parameter gesamt,
aber nur ~3 Mrd. **aktiv** pro Token:

- **RAM-Bedarf** richtet sich nach den 35B → 21 GB
- **Geschwindigkeit** richtet sich nach den 3B → ~1,9 GB pro Token

Deshalb ist ein MoE auf reiner CPU brauchbar schnell, wo ein dichtes Modell
gleicher Größe zäh wäre.

**Bandbreite ausrechnen:**

```
genutzte GB/s = tg_tokens_pro_sekunde × 1,9 GB
```

### 4.2 Thread-Sweep

| Threads | pp512 | tg128 |

| **12** | **99,79** | **20,51** |

**Optimum = 12 Threads**, also genau die Zahl der physischen Kerne. Das ist auch

### 4.3 Verhalten bei gefülltem Kontext

```bash
~/llama.cpp/build/bin/llama-bench -m ~/models/Qwen_Qwen3.6-35B-A3B-Q4_K_M.gguf \
  -p 0 -n 128 -d 0,4096,16384 -r 3
```

`-d` = Depth, also wie viel Kontext schon im KV-Cache liegt, bevor gemessen wird.

Alle Läufe mit `-fa 0` (siehe 4.3b).

| Kontext | tg128 | Verlust je Verdopplung |
|---|---:|---:|
| leer | 20,49 ± 0,14 | — |
| 4.096 | 18,70 ± 0,03 | −9 % |
| 16.384 | 14,89 ± 0,07 | −11 % |
| 32.768 | 12,39 (r=1) | −17 % |
| 65.536 | **8,86** (r=1) | −28 % |

**Eine glatte, gutartige Kurve.** Jede Verdopplung des Kontexts kostet 10–30 %,
mit wachsender Tendenz. Grund: zusätzlich zu den Modellgewichten muss bei jedem
Token der KV-Cache gelesen werden — alles, was bisher im Gespräch steht. Der
wächst linear mit dem Kontext, dazu kommt die Attention-Rechenarbeit über alle
bisherigen Positionen.

Hochgerechnet: **~6 t/s bei 128k, ~4 t/s bei 256k** (dem Maximum des Modells).
Selbst voller Kontext bleibt also benutzbar, nur langsam.

**Alltagsbild: 20 t/s frisch, 15 t/s nach längerem Gespräch, ~12 t/s bei 32k.**

### ⚠️ Wichtigste Lektion des Abends: Page Cache

Ein erster 64k-Lauf ergab **3,38 t/s** — Faktor 2,6 schlechter als der saubere
Wert von 8,86. Der Unterschied: währenddessen lief ein Download.

**Warum das so viel ausmacht:** llama.cpp lädt das Modell nicht in den
Programmspeicher, sondern per **mmap** — es sagt dem Kernel „blende mir diese
Datei als Speicherbereich ein". Ob die Daten dann wirklich im RAM liegen,
entscheidet allein der **Page Cache** (die Spalte `buff/cache` in `free -h`).

Schreibt ein Download mehrere GB auf die NVMe, macht der Kernel dafür Platz im
Page Cache — und wirft dabei Modellseiten raus. llama.cpp lädt sie dann mitten
in der Messung von der Platte nach. Gemessen wird plötzlich die NVMe statt des
RAMs.

**Regel: während einer Messung läuft sonst nichts.** Kein Download, kein Browser.
Vorher prüfen:

```bash
free -h
```

- `buff/cache` muss **größer als das Modell** sein
- `Swap` muss **nahe null** sein — wird ausgelagert, sind alle Werte wertlos
- `free` mit wenig Wert ist *kein* Problem: Linux füllt freien RAM absichtlich
  mit Page Cache. Die aussagekräftige Spalte ist `available`.

Ohne die Vergleichsmessung hätte man geglaubt, das System bricht bei langem
Kontext zusammen — und womöglich Hardware gekauft, um ein Problem zu lösen,
das es nicht gibt.

### 4.3b Flash Attention (`-fa`)

```bash
~/llama.cpp/build/bin/llama-bench -m ~/models/Qwen_Qwen3.6-35B-A3B-Q4_K_M.gguf \
  -p 0 -n 128 -d 32768 -fa 0,1 -r 1 --no-warmup
```

| Flash Attention | tg128 @ 32k |
|---|---:|
| **aus (`-fa 0`)** | **12,39** |
| an (`-fa 1`) | 9,66 (−22 %) |

**Auf CPU ist Flash Attention langsamer — also auslassen.**

Warum: Flash Attention ist für GPUs entworfen. Dort trennt die Hardware scharf
zwischen winzigem, sehr schnellem SRAM und großem, langsamem VRAM; der ganze
Trick besteht darin, Kacheln passend für dieses kleine schnelle Fenster zu
schneiden und die große Zwischenmatrix nie zu materialisieren.

Eine CPU hat eine andere Speicherlandschaft (64 MB L3, dazu L2/L1) und
verschiebt Daten automatisch zwischen den Ebenen. Die manuelle Kachelung bringt
dort nichts, ihr Verwaltungsaufwand bleibt aber.

Dazu: **beim Generieren gibt es nur eine einzige Query** gegen alle Keys. Es
entsteht gar keine große Zwischenmatrix, die man einsparen könnte — Flash
Attention löst hier ein Problem, das nicht existiert.

Beim *Einlesen* (pp) könnte das Bild anders aussehen, dort ist der Aufwand
quadratisch. Eigener Test, noch offen.

### 4.5 Modellvergleich — MoE gegen dicht

Alle mit `-r 3`, Standardeinstellungen, 12 Threads.

| Modell | Typ | Datei | Parameter | pp512 | tg128 |
|---|---|---:|---:|---:|---:|
| **Qwen3.6-35B-A3B Q4_K_M** | MoE, ~5 Bit | 21 GB | 35,5 B (3 B aktiv) | **100** | **20,5** |
| Bonsai-27B Q1_0 | dicht, 1 Bit | 3,6 GB | 26,9 B | 14,0 | 8,7 |
| Qwen3.6-27B Q4_K_M | dicht, ~5 Bit | 17 GB | 27,3 B | 16,1 | 3,9 |

**Das MoE ist sechsmal schneller beim Lesen und fünfmal beim Schreiben** als das
dichte Modell derselben Generation — obwohl seine Datei größer ist und es mehr
Parameter hat.

#### Drei verschiedene Flaschenhälse

**MoE Q4 — bandbreitenlimitiert, aber nicht am Anschlag.**
~1,9–2,3 GB aktive Gewichte pro Token → bei 20,5 t/s rund 39–47 GB/s.
Das sind nur ~60 % der Lesegrenze der Maschine.

**Dicht Q4 — bandbreitenlimitiert und am Anschlag.**
18 GB pro Token (die *komplette* Datei, bei jedem Token) → bei 3,91 t/s
rund **70 GB/s**. Das ist die reine Lesegrenze der Maschine, voll ausgefahren.

**Dicht 1 Bit — rechenlimitiert.**
Nur 3,8 GB pro Token → bei 8,74 t/s nur 33 GB/s, also weit unter der Grenze.
Hier bremst die Rechenarbeit. Entscheidend ist die **Rechendichte**:

| Modell | Bits/Gewicht | Gewichte pro Byte | Rechenoperationen pro Byte |
|---|---:|---:|---:|
| Q4_K_M | ~5 | 1,6 | 3,2 |
| Q1_0 | 1 | 8 | **16** |

Bei einem Bit pro Gewicht stecken acht Gewichte in einem Byte — fünfmal mehr
Rechenarbeit pro gelesenem Byte, dazu das Auspacken der einzelnen Bits per
Schiebeoperationen. Der Speicher ist dann nicht mehr das Problem, die CPU
verhungert an der Arbeit.

#### Korrektur: die Lesegrenze liegt bei ~70 GB/s, nicht 60

STREAMs `Triad` liest zwei Felder **und schreibt eines**. Schreiben ist für RAM
teurer als Lesen — die CPU muss eine Speicherzeile erst holen, bevor sie sie
ändern darf, selbst wenn sie komplett überschrieben wird. Ein Test mit
Schreibanteil unterschätzt daher die reine Lesebandbreite.

Das dichte Q4-Modell hat 70 GB/s erreicht und damit gezeigt, wo die echte
Lesegrenze liegt.

**Folge: beim MoE liegt womöglich noch Leistung in der Software.** Ein MoE liest
nicht linear, sondern springt bei jedem Token zu acht von 256 Experten. Solche
Sprünge kann die Vorablade-Logik der CPU nicht vorhersagen. Das dichte Modell
beweist, dass die Hardware mehr könnte.

#### Die eigentliche Lehre

Bonsai zeigt den Kompromiss bei extremer Quantisierung: fünfmal weniger Bytes
lesen bringt beim Schreiben das Doppelte — aber beim Lesen **nichts**, weil die
Rechenarbeit dieselbe bleibt. Der Engpass wird verschoben, nicht beseitigt.

Ein MoE beseitigt ihn: es überspringt 97 % des Modells und spart dadurch Bytes
**und** Rechenoperationen zugleich. Deshalb ist MoE für CPU-Inferenz die
richtige Modellklasse.

(Ungeprüft bleibt die **Qualität**. Ein Modell auf ein Bit pro Gewicht
einzudampfen kostet etwas — wie viel, sagt kein Geschwindigkeitstest.)

## 4.6 GPU-Test mit der RX 6600 (Vulkan)

|---|---|
| Modell | XFX Radeon RX 6600, Navi 23 (RDNA2), 8 GB GDDR6 (Hynix) |

### Vulkan-Build

```bash

cd ~/llama.cpp
cmake -B build-vulkan -DCMAKE_BUILD_TYPE=Release -DGGML_NATIVE=ON -DGGML_VULKAN=ON
cmake --build build-vulkan --config Release -j $(nproc)
```

Eigener Ordner — der CPU-Build in `build/` bleibt unberührt, beide sind
vergleichbar. Dauert länger als der CPU-Build, weil hunderte GLSL-Shader nach
SPIR-V übersetzt werden müssen.

Vorher prüfen, dass Vulkan die Karte sieht (nicht `llvmpipe`, den Software-Renderer):

```bash
vulkaninfo --summary
~/llama.cpp/build-vulkan/bin/llama-bench --list-devices
```

**Warum Vulkan statt ROCm:** ROCm ist schneller, aber mehrere GB groß, und die
RX 6600 (gfx1032) steht nicht auf AMDs offizieller Unterstützungsliste. Vulkan
sind drei kleine Pakete und läuft auf jeder Karte.

### Ergebnis 1: ganze Schichten verschieben (`-ngl`) — funktioniert nicht

| `-ngl` | pp512 | tg128 |
|---:|---:|---:|
| CPU-Build | 100 | **20,5** |
| 0 | 138,9 | 16,2 |
| 4 | 145,7 | 16,0 |
| 8 | 159,9 | 15,1 |

**Zwei Überraschungen:**

**pp ist schneller, obwohl bei `-ngl 0` kein einziges Gewicht im VRAM liegt.**
Grund ist **Op-Offload**: llama.cpp schickt große Matrixmultiplikationen an die
GPU, auch wenn die Gewichte im RAM liegen — es kopiert sie kurz über PCIe.
Beim Einlesen lohnt sich das, weil ein Gewicht nach einer Übertragung 512-mal
benutzt wird.

**tg wird schlechter, je mehr Schichten auf der Karte liegen.** Beim Schreiben
wird ein Gewicht nach der Übertragung nur *einmal* benutzt — die Kopie über
PCIe kostet mehr, als die schnellere Rechnung einbringt. PCIe 4.0 ×8 sind ~16 GB/s,
ein Viertel dessen, was die CPU aus dem RAM holt.

### Ergebnis 2: gezielt aufteilen (`-ncmoe`) — funktioniert

`-ngl 99 -ncmoe N` = alle Schichten auf die GPU, aber die **Experten** von N
Schichten zurück in den RAM.

Der Grund, warum das besser ist: eine Schicht besteht aus Attention und
gemeinsamen Gewichten (klein, bei *jedem* Token gebraucht) und den 256 Experten
(riesig, pro Token werden 8 benutzt). Über 90 % der Bytes sind Experten. Ganze
Schichten zu verschieben füllt den VRAM also mit Daten, die zu 97 % ungenutzt
bleiben.

| `-ncmoe` | pp512 | tg128 |
|---:|---:|---:|
| 41 | 158,3 | 19,4 |
| 38 | 166,1 | 23,6 |
| **36** | 168,5 | **24,0** |
| 34 | **181,4** | 21,5 |
| 32 | 66,3 ⚠️ | 17,0 |
| 30 | 64,2 ⚠️ | 17,5 |

**Die VRAM-Kante liegt zwischen 34 und 32.**

### ⚠️ Die zweite große Falle: stiller VRAM-Überlauf

Bei `-ncmoe 32` und `30` fällt pp auf ~65 t/s — **schlechter als reine CPU**.

Passt die Konfiguration nicht ins VRAM, bricht der Treiber **nicht ab**. Er
lagert stillschweigend in den Systemspeicher aus und greift über PCIe darauf zu
— 16 GB/s statt 224. Es gibt keine Fehlermeldung, nur plötzlich miserable Werte.

**Wenn eine GPU-Konfiguration unerklärlich langsam ist, ist das fast immer die
Ursache.**

### Wo der Kontext landet

Mit `-ngl 99` liegen die Attention-Teile auf der Karte — und **der KV-Cache
gehört dorthin, wo die Attention liegt**. Der Kontext konkurriert also direkt
mit den Experten um dieselben 6,3 GB.

| Kontext | KV-Cache im VRAM |
|---|---:|
| 4k | ~0,08 GB |
| 16k | ~0,3 GB |
| 32k | ~0,65 GB |
| 64k | ~1,3 GB |

**Achtung bei Benchmarks:** llama-bench arbeitet standardmäßig mit winzigem
Kontext. Werte ohne `-d` gelten für einen Zustand, den man im Alltag nie hat.

Gegenmittel bei knappem VRAM, falls nötig: `--no-kv-offload` / `-nkvo` lässt den
Kontext im RAM, macht die Attention aber langsamer.

### Ergebnis 3: der Vorsprung wächst mit dem Kontext

| | CPU | GPU (`-ncmoe 36`) | Gewinn |
|---|---:|---:|---:|
| Schreiben, leer | 20,5 | **24,0** ± 0,21 | +17 % |
| Schreiben, 16k | 14,9 | **20,4** ± 0,70 | **+37 %** |
| Lesen (pp512) | 100 | **181** | +81 % |

**Warum der Gewinn bei langem Kontext größer wird:** Der Einbruch von 20,5 auf
14,9 kam auf der CPU vor allem von der Attention-Rechnung über den bisherigen
Text. Genau dieser Teil liegt jetzt auf der Karte, mit dem KV-Cache im VRAM.
Die Experten bremsen weiterhin, aber der zusätzliche Kontext-Aufwand kostet
fast nichts mehr.

**Die GPU repariert genau die Schwäche, die die CPU bei langen Gesprächen hat**
— und das mit einer 8-GB-Karte, auf die nicht mal ein Drittel des Modells passt.

### 👉 Empfohlene Einstellung

```bash
~/llama.cpp/build-vulkan/bin/llama-cli -m ~/models/Qwen_Qwen3.6-35B-A3B-Q4_K_M.gguf \
```

`-ncmoe 38` statt 36: praktisch gleich schnell (23,6 gegen 24,0, im Rauschen),

### Messhinweis: Streuung zwischen Läufen

`-ncmoe 36` ergab in drei Läufen 20,67 / 23,91 / 24,00. Die Streuung *innerhalb*
eines Laufs war jeweils winzig (±0,01 bis ±0,43) — es schwankt also zwischen den
Läufen, nicht innerhalb. Vermutliche Ursache: wie viel VRAM der Desktop beim
Start gerade belegt.

**Lehre: bei Konfigurationen nahe der VRAM-Kante mehrfach messen.** Ein einzelner
Lauf kann um 15 % danebenliegen, ohne dass die Streuung es verrät.

## 5. Die Auswertung

### Wo der Flaschenhals liegt

| Größe | Wert |
|---|---:|
| Theoretisch aus 8 Kanälen DDR4-3200 | ~205 GB/s |
| **Tatsächlich erreichbar (STREAM, 12 Threads)** | **~60 GB/s** |
| Davon von llama.cpp genutzt | ~39 GB/s (65 %) |

**Der RAM ist nicht das Problem.** Die 8 Kanäle könnten 205 GB/s liefern, die
Maschine holt aber nur 60 ab. Drei Ursachen:

1. **Begrenzte Zugriffe pro Kern.** Jeder Kern kann nur ~20 Speicheranfragen
   gleichzeitig offen halten, danach wartet er. Ein Zen-2-Kern schafft dadurch
   nur rund 4–6 GB/s — mal 12 Kerne ergibt die beobachtete Größenordnung.
2. **Nur 2 Chiplets.** Jedes Chiplet hat eine eigene Leitung zum Speicher-
   Controller, und die deckelt bei Zen 2 um 30–50 GB/s. Bild: acht Zapfsäulen
   am Tank, aber nur zwei Schläuche.
3. **MoE springt im Speicher herum** statt linear zu lesen. Deshalb erreicht
   llama.cpp nur 65 % dessen, was STREAM mit stur linearem Zugriff schafft.

**Der Beweis, dass die CPU limitiert und nicht der RAM:** die STREAM-Kurve steigt
bei 12 Threads immer noch. Sie flacht nicht ab — sie hört auf, weil die Kerne
ausgehen. Wäre der Speicher am Limit, läge dort ein Plateau.

### Konsequenz

- Mehr RAM-Riegel bringen **nichts** — die Bestückung ist bereits optimal
- Eine CPU mit **mehr Chiplets** bringt direkt mehr Tokens/s
- An der Software ist wenig zu holen: 65 % Wirkungsgrad bei MoE ist solide

## 6. CPU-Aufrüstung — Analyse

Regel: **die Chiplet-Zahl bestimmt das Schreiben, die Kernzahl das Lesen.**
Für die vollen ~200 GB/s der 8 Kanäle braucht es 8 Chiplets.

### Threadripper PRO 3000 (Zen 2)

| CPU | Kerne | Chiplets | Bandbreite | tg | pp | Preis (gebraucht) |
|---|---:|---:|---:|---:|---:|---:|
| **3945WX** ← aktuell | 12 | 2 | **60** ✓ | **20,5** ✓ | **100** ✓ | — |
| 3955WX | 16 | 2 | ~75 | ~25 | ~130 | 169 € |
| 3975WX | 32 | 4 | ~120 | ~40 | ~230 | 500–1000 € |
| 3995WX | 64 | 8 | ~190 | ~55–65 | ~400 | 1300 € |

### Threadripper PRO 5000 (Zen 3)

| CPU | Kerne | Chiplets | Bandbreite | tg | pp | Preis |
|---|---:|---:|---:|---:|---:|---:|
| 5945WX | 12 | 2? | ~65 | ~22 | ~120 | ? |
| 5955WX | 16 | 2? | ~75 | ~25 | ~155 | ? |
| 5965WX | 24 | 4 | **124** ✓ | ~42 | ~230 | 1000 € |
| 5975WX | 32 | 4 | ~125 | ~42 | ~290 | ? |
| 5995WX | 64 | 8 | ~190 | ~55–65 | ? | ? |

✓ = gemessen. **Alles andere ist Hochrechnung**, basierend auf der Chiplet-Regel
und dem gemessenen llama.cpp-Wirkungsgrad von 65 %.

### Fazit

Es gibt nur **drei Bandbreitenklassen**:

| Klasse | tg | günstigster Vertreter |
|---|---:|---|
| 2 Chiplets | 20–25 | aktueller Stand |
| 4 Chiplets | ~40 | **3975WX, 500 €** |
| 8 Chiplets | ~60 | **3995WX, 1300 €** |

- **Der 3955WX (169 €) lohnt nicht** — gleiche 2 Chiplets, der Vorteil liegt nur
  beim Lesen, und das übernimmt künftig die GPU.
- **Die 5000er-Klasse lohnt nicht** — der 5965WX hat dieselben 4 Chiplets wie der
  3975WX, kostet aber das Doppelte. Der Zen-3-Vorteil liegt in der Rechenleistung,
  also wieder beim Lesen. Dazu käme ein nötiges BIOS-Update.
- **Innerhalb einer Chiplet-Klasse ändert sich beim Schreiben fast nichts.** Ein
  5975WX mit 32 Kernen schreibt so schnell wie ein 5965WX mit 24.

**Empfehlung: erst die RTX 5070 Ti abwarten.** Danach ist klar, wie viel Arbeit
überhaupt noch an der CPU hängt — genau die Größe, die eine neue CPU
beschleunigen würde. Vorher kauft man blind.

## 7. Wenn die RTX 5070 Ti da ist

Die Karte hat **16 GB VRAM**, das Modell braucht 21 GB — passt also nicht ganz.

- **Beim Lesen (pp)** hilft die GPU fast immer und massiv. Aus 100 t/s können
  700–1000 werden.
- **Beim Schreiben (tg)** hilft sie anteilig: der Teil im VRAM wird mit ~900 GB/s
  gelesen, der Rest bleibt bei ~39 GB/s. Der langsame Teil dominiert.
- **MoE-Trick:** die kleinen, bei jedem Token gebrauchten Teile (Attention,
  gemeinsame Layer) auf die GPU, die großen Experten im RAM lassen — in
  llama.cpp über `--n-cpu-moe`. Holt bei begrenztem VRAM überproportional viel raus.
- Ein Quant, das **vollständig** ins VRAM passt (`IQ4_XS` 19,7 GB knapp,
  `Q3_K_M` 17,1 GB sicher), wäre nicht dreimal, sondern eher zwanzigmal so schnell.

**llama.cpp muss dafür neu gebaut werden** mit `-DGGML_CUDA=ON`. Blackwell
braucht ein aktuelles CUDA-Toolkit.

### Was der RX-6600-Test dafür schon gezeigt hat

Der Ablauf ist derselbe, die Erkenntnisse übertragen sich direkt:

1. **`-ncmoe` statt `-ngl`.** Ganze Schichten zu verschieben hat `tg`
   *verschlechtert* (20,5 → 15,1). Gezielt die Experten im RAM lassen hat es
   verbessert (→ 24,0). Bei 16 GB kann man mehr Experten mitnehmen, das Prinzip
   bleibt.
2. **Den Sweep fahren, nicht raten.** `-ncmoe` in Zweierschritten durchtesten,
   bis der Absturz kommt, dann zwei Stufen Sicherheitsabstand nehmen.
3. **Immer mit `-d` messen.** Ohne Kontext gemessene Werte gelten für einen
   Zustand, den man nie hat — und der KV-Cache belegt VRAM, das dann den
   Experten fehlt.
4. **Auf den stillen Überlauf achten.** Keine Fehlermeldung, nur plötzlich
   schlechtere Werte als auf reiner CPU.
5. **Mehrfach messen** bei Konfigurationen nahe der VRAM-Kante.

**Erwartung mit 16 GB:** grob die doppelte Menge Experten auf der Karte
gegenüber der RX 6600, dazu ~4× Bandbreite (900 statt 224 GB/s) und ~20×
Rechenleistung. `tg` sollte deutlich über die 24 hinausgehen, `pp` in den
mehrere-hundert-Bereich.

Der große Sprung käme aber erst mit einem Quant, das **komplett** ins VRAM
passt — dann fällt der RAM als Begrenzer ganz weg.

## 8. Noch offen

### Erledigt ✓

- Kontext-Test (4.3) — Kurve bis 64k vermessen
- Flash Attention (4.3b) — auf CPU langsamer, auslassen
- Dicht gegen MoE (4.5) — MoE gewinnt fünf- bis sechsfach
- Bonsai / ternär (4.5) — läuft mit Standard-llama.cpp, rechenlimitiert
- GPU mit Vulkan (4.6) — `-ncmoe` bringt +17 bis +81 %

### Offen

- **Quant-Vergleich Q4 gegen Q8** — Q8_0 (37 GB) hat doppelt so viele Bytes.
  Läuft es halb so schnell, ist die Bandbreiten-Abhängigkeit direkt belegt.
  Passt gerade noch in die 61 GB, `free -h` im Auge behalten.
- **Flash Attention beim *Einlesen*** — auf CPU beim Schreiben schädlich, aber
  pp ist quadratisch, dort könnte es helfen. Eigener Test mit `-p 2048,8192 -fa 0,1`.
- **Kontext-Grenze auf der GPU** — bei 16k hält `-ncmoe 36` noch. Ab wann kippt
  es? Test mit `-d 32768,65536` und Blick auf den VRAM.
- **Bonsai-Qualität** — Geschwindigkeit ist gemessen, Qualität nicht. Ein Modell
  auf 1 Bit pro Gewicht einzudampfen kostet etwas; wie viel, sagt kein Benchmark.
- **`-fitt` ausprobieren** — llama.cpp rechnet selbst aus, wie viel ins VRAM
  passt: `-fitt 512` lässt 512 MiB Reserve.
- **RTX 5070 Ti** — siehe Abschnitt 7. Der Ablauf ist derselbe wie mit der
  RX 6600, nur mit CUDA-Build und 16 statt 8 GB.

## 9. Nützliche Befehle

```bash
# Standardlauf
llama-bench -m MODELL.gguf

# Thread-Sweep
llama-bench -m MODELL.gguf -t 6,8,12,16,24 -r 3

# Verhalten bei gefülltem Kontext (-d = wie viel Kontext schon drin liegt)
llama-bench -m MODELL.gguf -p 0 -n 128 -d 0,4096,16384

# Mehrere Modelle vergleichen — einfach mehrere -m
llama-bench -m A.gguf -m B.gguf

# Ausgabe als CSV
llama-bench -m MODELL.gguf -o csv

# Alle Optionen der installierten Version
llama-bench --help
```

### Überwachung

```bash
watch -n 1 sensors               # Temperaturen; k10temp = CPU, Tccd* = Chiplets
sudo ipmitool sensor list        # Lüfterdrehzahlen, Spannungen über den BMC
free -h                          # buff/cache muss > Modellgröße sein
```

### Fallstricke, die Messungen ruinieren

1. **Debug-Build** — ohne `-DCMAKE_BUILD_TYPE=Release` misst man Faktor 5–10 daneben
2. **Kalter Page Cache** — der erste Lauf lädt das Modell von der NVMe, verwerfen
3. **Hintergrundlast** — Browser zu. Große `±`-Werte verraten Störungen
4. **Throttling** — erst ab ~95 °C ein Thema, hier unkritisch (72 °C unter Last)
5. **Swap** — wenn das Modell nicht in den RAM passt, brechen die Werte komplett ein

## 10. Nebenbefunde zum System

- **Netzwerk:** die beiden Onboard-Ports sind `enp210s0` und `enp211s0`. Ein
  Kabel steckte anfangs im BMC-Management-Port — dort gibt es Link, aber das
  Betriebssystem sieht nichts davon. Über `enp211s0` läuft Gigabit.
- **BMC:** ohne Netzwerk erreichbar über `/dev/ipmi0`. `sudo apt install ipmitool`,
  dann `sudo ipmitool sensor list`. Die Weboberfläche bräuchte ein Kabel im
  dritten (Management-) Port.
- **Lüfter:** `MOS_FAN1` läuft konstant mit 5600 RPM bei 34 °C VRM — unnötig, aber
  nicht hörbar. `CPU_FAN1` (Radiator) mit 1700–2100 RPM ist die Lärmquelle.
  Beides nur im BIOS regelbar: *H/W Monitor → Fan Configuration*. Die Pumpe
  (`CPU_FAN2/WP`) dabei auf Full Speed lassen.
- **Screenshot:** Mac-Tastatur sendet auf F13 ein `XF86Tools`, das GNOME auf
  „Settings öffnen" legt. Deshalb neu gelegt auf `Super+Shift+S`:
  ```bash
  gsettings set org.gnome.shell.keybindings show-screenshot-ui "['<Super><Shift>S']"
  ```
- **Zwischenablage:** `wl-clipboard` war nicht installiert, deshalb ging Kopieren
  aus Claude Code nicht. `sudo apt install wl-clipboard` behebt das.
