## 2. Qwen3.6-35B-A3B mit zwei Karten

Das MoE (20,74 GiB) passt jetzt **vollständig ins VRAM**. `--n-cpu-moe` — am
28.07. noch der entscheidende Hebel — entfällt damit ersatzlos.

`llama-bench -ngl 99 -ctk q8_0 -ctv q8_0 -fa 1`:

| Test | t/s |
|---|---:|
| pp512 | 4698,33 ± 30,68 |
| tg128 | 204,54 ± 1,63 |
| pp512 @ d8192 | 4355,74 ± 22,14 |
| tg128 @ d8192 | 193,96 ± 1,20 |
| pp512 @ d32768 | 3632,18 ± 45,47 |
| tg128 @ d32768 | 159,06 ± 0,80 |

### 2.1 Faktor 2 gegenüber einer Karte

`llama-cli` unter den Bedingungen von 5.5 (28.07.), nur ohne `--n-cpu-moe`:

| | Generation |
|---|---:|
| 1 Karte, `--n-cpu-moe 10` (28.07.) | 113,5 t/s |
| **2 Karten, alles im VRAM** | **223,6 t/s** |

**Faktor 1,97.** Der Gewinn kommt *nicht* vom Parallelrechnen — bei Layer-Split
arbeiten die Karten abwechselnd, nie gleichzeitig. Er kommt daher, dass die
letzten Experten-Tensoren nicht mehr über den RAM müssen.

### 2.2 MTP verliert beim MoE seinen Nutzen

204,5 t/s ohne MTP (`llama-bench`) gegen 223,6 t/s mit MTP (`llama-cli`) sind
nur noch **rund +9 %** — am 28.07. waren es beim dichten 27B +95 %.

> **Vorbehalt:** Die beiden Zahlen stammen aus verschiedenen Werkzeugen und sind
> streng genommen nicht direkt vergleichbar. Die Größenordnung ist aber
> eindeutig, und die Erklärung trägt:

MTP zahlt sich nur aus, solange `tg` **bandbreitenlimitiert** ist. Gerechnet:
pro Token werden ~1,75 GB gelesen, bei 204 t/s also ~358 GB/s — und da bei
Layer-Split immer nur eine Karte rechnet, sind das **~40 % der 896 GB/s**. Das
MoE ist im VRAM also **rechen-/overheadlimitiert**, und dann kostet das Prüfen
der Entwurfstoken echte Zeit, statt gratis mitzulaufen.

### 2.3 Kontextabfall ist flach

204,5 → 194,0 (8k, −5 %) → 159,1 t/s (32k, **−22 %**). Das dichte 27B verlor
schon von 640 auf 8192 Token 31 %. Der in 5.5 vermutete strukturelle Vorteil des
MoE bei langem Kontext ist damit belegt.

## 3. Laguna S 2.1 — 118B auf 31 GiB VRAM

Poolside, veröffentlicht 21.07.2026, MoE, Open Weights (OpenMDW-1.1).

### 3.1 Modell-Metadaten

Direkt aus dem GGUF-Header gelesen:

| Schlüssel | Wert |
|---|---:|
| `block_count` | 48 |
| `expert_count` | **256** |
| `expert_used_count` | **10** |
| `embedding_length` | 3072 |
| `attention.head_count_kv` | 8 |
| `attention.key_length` / `value_length` | 128 / 128 |
| `expert_feed_forward_length` | 1024 |
| `context_length` | 262144 |
| `leading_dense_block_count` | 1 |

KV-Cache: (128+128) × 8 = 2048 Werte → 2048 B je Layer und Token in q8_0.

**Entscheidend ist aber die Sliding-Window-Attention.** Die `config.json` zeigt
`sliding_window: 512` und in `layer_types` sind von 48 Schichten nur **12 mit
vollem Kontext**, die übrigen 36 sehen nur 512 Token:

```
KV(ctx) = 2048 B × (12 × ctx + 36 × 512)
```

| Kontext | naiv (alle 48 Layer voll) | **tatsächlich** |
|---:|---:|---:|
| 32.768 | 3,0 GiB | **0,8 GiB** |
| 65.536 | 6,0 GiB | **1,5 GiB** |
| 131.072 | 12,0 GiB | **3,1 GiB** |
| 262.144 (Maximum) | 24,6 GiB | **6,1 GiB** |

> **Korrektur:** Die erste Fassung dieses Abschnitts rechnete alle 48 Schichten
> mit vollem Kontext und kam damit auf das Vierfache. **Der volle 262k-Kontext
> ist erreichbar** und kostet 6 GiB, nicht 25. Das erklärt auch den flachen
> Kontextabfall von nur 11 % (siehe 5).

### 3.2 Quant-Wahl: die offizielle Datei passt nicht

| Variante | Größe |
|---|---:|
| Poolside Q4_K_M (offiziell) | **89,0 GiB** |
| unsloth UD-Q4_K_M | **68,1 GiB** |
| unsloth UD-IQ4_XS | 53,6 GiB |

Budget: 31 GiB VRAM + ~54 GiB RAM = 85 GiB. Poolsides eigene Datei passt damit
**nicht** und würde von der SSD gepaged. Unsloths „UD"-Quantisierung (wichtige
Schichten feiner, unwichtige gröber) liefert dasselbe Q4_K_M in 68,1 GiB.

**Gewählt: unsloth UD-Q4_K_M.**

## 4. Die vier Fallstricke beim Aufsetzen

### 4.1 Upstream-llama.cpp kennt die Architektur nicht

Laguna braucht Poolsides Fork, Branch `laguna`
(`github.com/poolsideai/llama.cpp`). In einen **eigenen** Baum klonen —
`~/llama.cpp` mit den Benchmark-Bäumen bleibt unangetastet:

```bash
git clone -b laguna --depth 1 https://github.com/poolsideai/llama.cpp ~/llama.cpp-laguna
cd ~/llama.cpp-laguna
cmake -B build-cuda -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=120
cmake --build build-cuda -j $(nproc)
```

### 4.2 Der Fork baut nicht mit GCC 15

Bei 65 %:

```
common/speculative.cpp:1091:35: error: 'isfinite' is not a member of 'std'
```

Fehlender Include. Behoben durch `#include <cmath>` in
`common/speculative.cpp`. Betroffen ist ausgerechnet der DFlash-Code. Danach
läuft der Build ohne Neustart durch (`cmake --build` macht bei 65 % weiter).

### 4.3 `LLAMA_ARG_SPEC_TYPE` aus der `.bashrc` bricht den Start ab

```
W llama_init_from_model: context type MTP requested but model doesn't contain MTP layers
E srv    load_model: failed to create MTP context
```

Ursache ist `~/.bashrc` Zeile 119 — die **Empfehlung aus FINDINGS 5.4**:

```bash
export LLAMA_ARG_SPEC_TYPE=draft-mtp
```

Sie wirkt auf *jeden* `llama-server`-Aufruf. Laguna hat keinen MTP-Kopf (es
nutzt DFlash), also bricht der Start ab. Umgehung pro Aufruf:

```bash
env -u LLAMA_ARG_SPEC_TYPE ~/llama.cpp-laguna/build-cuda/bin/llama-server ...
```

> **Empfehlung: die Zeile aus der `.bashrc` entfernen** und `--spec-type
> draft-mtp` stattdessen direkt in die Qwen-Aufrufe schreiben. Eine global
> gesetzte modellspezifische Option ist eine Zeitbombe, sobald ein zweites
> Modell dazukommt.

### 4.4 Layer-Split verteilt nach Anzahl, nicht nach Größe

```
E ggml_backend_cuda_buffer_type_alloc_buffer: allocating 21521.55 MiB on device 1: out of memory
```

**Der wichtigste Befund dieses Durchgangs.** llama.cpp teilt die Layer
gleichmäßig auf (24/24). Durch `--n-cpu-moe 34` sind die Layer aber völlig
ungleich groß:

- Layer 0–33: Experten im RAM → auf der GPU fast nichts
- Layer 34–47: Experten auf der GPU → je ~1,35 GiB

Karte 0 bekommt lauter Leichtgewichte, Karte 1 **alle 14 schweren auf einmal** →
21,5 GiB angefordert, 15,8 GiB vorhanden.

**Lösung: `-ts 40,8`** — Karte 0 nimmt 40 Layer, Karte 1 nur 8, dann trägt jede
sieben schwere:

| | Experten | KV | gesamt (gerechnet) | gemessen |
|---|---:|---:|---:|---:|
| Karte 0 (40 Layer) | 8,1 GiB | 2,5 GiB | ~10,6 GiB | **14,92 GiB** |
| Karte 1 (8 Layer) | 10,8 GiB | 0,5 GiB | ~11,3 GiB | **13,32 GiB** |

Die Messung liegt über der Rechnung — Compute-Buffer und Fragmentierung kosten
mehr als veranschlagt. Die Aufteilung stimmt trotzdem, beide Karten bleiben
unter 15,92 GiB.

Zusätzlich meldet der Loader:

```
W tensor overrides to CPU are used with mmap enabled - consider using --no-mmap
```

Mit gezielten CPU-Overrides arbeitet `mmap` gegen einen: Die Teile werden über
Seitenfehler von der SSD nachgeladen, statt einmal im RAM zu liegen.
**`--no-mmap` ist bei `--n-cpu-moe` Pflicht, nicht Kür.**

### 4.5 Der funktionierende Aufruf

```bash
env -u LLAMA_ARG_SPEC_TYPE ~/llama.cpp-laguna/build-cuda/bin/llama-server \
  -m ~/models/laguna/Laguna-S-2.1-UD-Q4_K_M-00001-of-00003.gguf \
  -ngl 99 --n-cpu-moe 34 -ts 40,8 --no-mmap \
  -c 32768 -ctk q8_0 -ctv q8_0 -fa 1 --jinja \
  --host 127.0.0.1 --port 8080
```

Nur Teil 1 angeben, llama.cpp zieht die übrigen Teile selbst nach.

3. Token-Generierung ist speicher-, nicht rechenlastig

Die niedrige Leistungsaufnahme ist also **kein Fehler, sondern die Signatur des

## 6. TurboQuant — geprüft, nicht verfügbar

TurboQuant (Google DeepMind, ICLR 2026) komprimiert den KV-Cache per
Walsh-Hadamard-Rotation um das 4–5-fache bei ~1 % Qualitätsverlust. Für Laguna
wären das:

| Cache | je Token | 128k Kontext |
|---|---:|---:|
| q8_0 (aktuell) | 96 KiB | 12,0 GiB |
| iq4_nl | 48 KiB | 6,0 GiB |
| tq3_0 (TurboQuant) | ~22 KiB | 2,8 GiB |

**Beide Bäume unterstützen es nicht.** Die erlaubten Cache-Typen sind
`f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1` — kein `tq3_0`.

> **Falle:** Ein `grep` nach `tq2_0` liefert Treffer, aber das ist *ternäre*
> Quantisierung für BitNet-Modelle, nicht TurboQuant. Verlässlich ist nur die
> Liste in `llama-server --help`.

Es existiert bisher nur in Forks (`animehacker/llama-turboquant`,
`AmesianX/TurboQuant`, `AtomicBot-ai/atomic-llama-cpp-turboquant`); im offiziellen
llama.cpp gibt es dazu nur eine Diskussion. Eine Zusammenführung mit Poolsides
`laguna`-Branch wäre echte Merge-Arbeit. **Sofort verfügbar ist `iq4_nl`** —
halb so groß wie `q8_0`, also etwa ein Viertel des TurboQuant-Nutzens gratis.

## 7. Tool Use — erster Aufbau

`llama-server` allein kann keine Tools ausführen. Nötig sind drei Teile:

1. `llama-server` **mit `--jinja`** — ohne das keine strukturierten Tool-Calls
2. ein Client, der die Werkzeuge **definiert** und mitschickt
3. derselbe Client, der die Aufrufe **ausführt**

Das Modell schreibt nie eine Datei; es gibt nur aus, welches Werkzeug mit
welchen Argumenten aufgerufen werden soll.

Geschrieben: `~/llm-agent/agent.py` — ohne externe Abhängigkeiten, Werkzeuge
`write_file` / `read_file` / `list_files`, alle Pfade auf `AGENT_WORKDIR`
beschränkt, Antworten werden gestreamt.

### 7.1 Zwei Fallen

**Die Web-UI hat keine Tools.** Im Browser antwortet das Modell wahrheitsgemäß,
es könne keine Dateien speichern — dort werden schlicht keine `tools`
mitgeschickt. Tool Use gibt es nur über den Client.

**`max_tokens` schneidet Tool-Calls ab.** Mit 4096:

```
Failed to parse tool call arguments as JSON: parse error at column 11250:
missing closing quote
```

Ganze Programmdateien sprengen 4096 Token mühelos; der abgeschnittene Call ist
kaputtes JSON und der Server wirft ihn mit HTTP 500 zurück. Auf 16384 erhöht.
Dieselbe Falle wie `-n 200` bei `llama-cli` (FINDINGS 5.6).

## 8. Praxislauf — „baue ein Auto-Rennspiel"

Identischer Prompt wie beim Qwen-Lauf vom 28.07., um vergleichbar zu bleiben.

**Was Laguna von sich aus tat:**

```
/home/fran/spiele/
├── requirements.txt          pygame>=2.5.0
└── rennspiel/
    ├── main.py               692 Zeilen
    └── README.md             Anleitung
```

Ordnerstruktur, getrennte Abhängigkeiten, Dokumentation — nichts davon stand im
Prompt. `main.py` wurde einmal überschrieben, das Modell hat seinen eigenen Code
also überarbeitet. Verbrauch: 28.914 von 32.768 Token Kontext (**88 %**).

**Das Ergebnis stürzt ab.** Nach wenigen Sekunden Spielzeit:

```
File "main.py", line 396, in zeichne_partikel
    pygame.draw.circle(surface, farbe, ...)
ValueError: invalid color argument
```

Ursache in `erzeuge_partikel`:

```python
min(255, farbe[0] + random.randint(-50, 50))   # nur nach oben begrenzt
```

Bei dunkler Grundfarbe (z. B. 30) und −50 ergibt das **−20**. Behoben durch
beidseitiges Begrenzen:

```python
pfarbe = tuple(max(0, min(255, k + random.randint(-50, 50))) for k in farbe[:3])
```

### 8.1 Qualitätsvergleich

**Das Ergebnis von Qwen3.6-27B war subjektiv deutlich besser.** Damit hält die
Daumenregel aus FINDINGS 6 auch gegen ein 118B-Modell:

| Modell | gesamt | aktiv/Token |
|---|---:|---:|
| Qwen3.6-27B dicht | 27 Mrd. | **27 Mrd.** |
| Laguna S 2.1 | 118 Mrd. | 8 Mrd. |

Entscheidend für die Ausgabequalität sind die **aktiven** Parameter, nicht die
gesamten. Das ist ein stärkerer Beleg als der Vergleich innerhalb der
Qwen-Familie, weil hier ein viermal größeres MoE gegen ein kleines dichtes
Modell verliert.

**Wo Laguna vorn lag, ist eine andere Fähigkeit:** Werkzeuggebrauch,
Projektstruktur, Selbstkorrektur. Qwen schrieb den besseren Code, Laguna
*arbeitete* besser. Zwei Dimensionen, die man nicht gegeneinander verrechnen
sollte.

### 8.2 Der eigentliche Befund

Laguna erklärte das Ergebnis für „komplett und fehlerfrei" — es stürzt beim
ersten Zusammenstoß ab. Genau die Sorte Fehler, die kein Modell findet, weil es
den Code **nie ausführt**.

> **Für ein Agentensystem heißt das: Ein Werkzeug, das erzeugten Code startet
> und die Fehlermeldung zurückgibt, bringt mehr als jedes größere Modell.**

## 9. DeepSeek V4 Flash — Versuch, Diagnose, Abbruch

Nach Laguna der Versuch, noch eine Klasse höher zu gehen. **Ergebnis: gescheitert
— aber die Diagnose ist der wertvollste Befund dieses Durchgangs.**

### 9.1 Modell und Quant-Wahl

`unsloth/DeepSeek-V4-Flash-0731-GGUF`, erschienen 31.07.2026,
`general.architecture = deepseek4`. **`LLM_ARCH_DEEPSEEK4` war im vorhandenen
Upstream-Build bereits enthalten** — kein Fork nötig, anders als bei Laguna.

| | |
|---|---:|
| Layer | 43 |
| Experten | 256, davon **6 + 1 geteilter** aktiv |
| `num_key_value_heads` | **1** |
| `sliding_window` | 128 |
| KV-Cache bei 32k | **1,3 GiB** |

Der KV-Cache ist damit fast vernachlässigbar. Das Problem ist die Modellgröße:

| Quant | Größe | passt? |
|---|---:|---|
| **UD-IQ1_S** | **76,9 GiB** | ja, mit 2,8 GiB Rest |
| UD-IQ1_M | 80,9 GiB | nein |
| UD-IQ4_XS | 128,4 GiB | nein (bräuchte 128 GB RAM) |

Es blieb also nur die 1-Bit-Fassung.

### 9.2 Zwei Fehlstarts

Dasselbe Layer-Split-Problem wie bei Laguna (4.4), nur mit teureren Layern:

```
--n-cpu-moe 29 -ts 36,7  →  allocating 18939 MiB on device 0: out of memory
--n-cpu-moe 35 -ts 39,4  →  läuft
```

Die Expertenschichten kosten hier **~2,7 GiB statt der geschätzten 1,8 GiB**,
weil bei IQ1_S die Attention-Tensoren und die Embedding-Matrix in höherer
Präzision bleiben. Belegung am Ende: **15637 MiB auf Karte 0, 8066 MiB auf
Karte 1** — Karte 1 blieb zur Hälfte ungenutzt, die Aufteilung war nicht
ausgereizt.

### 9.3 Messung: 2,6–2,8 t/s

Zum Vergleich: Laguna erreicht 25 t/s, das MoE im VRAM 204 t/s.

### 9.4 Die Diagnose — CPU-gebunden, nicht speichergebunden

Drei Messungen während der Generierung:

| Verdächtiger | Messung | Urteil |
|---|---|---|
| SSD-Paging | 0,94 GiB in 44 s (~22 MB/s) | **nicht die Ursache** |
| GPU | 3–5 % Auslastung, 50 W von 300 W | **langweilt sich** |
| **CPU** | 12 Kerne bei 71–100 %, `Load avg 12,60` | **Anschlag** |

Die 52 % Gesamtauslastung täuschen: llama.cpp fährt einen Thread je physischem
Kern, also 12 von 24 logischen — in `btop` stehen exakt zwölf Balken am
Anschlag, die SMT-Geschwister leer.

**Ursache ist die IQ1_S-Dequantisierung.** 1-Bit-Gewichte müssen für jede
Rechenoperation entpackt werden; das kostet mehr Zeit, als das Lesen der Bytes
dauert. Dasselbe Muster wie bei Bonsai-27B Q1_0 am 25.07. (dort: nur 44 %
Bandbreitenausnutzung).

> **Gegenprobe:** Chrome schließen senkte den Swap von 3,42 auf 1,44 GiB und
> änderte an den 2,6 t/s **nichts**. Speicherdruck war also nicht der Engpass.

### 9.5 Korrektur einer Fehlprognose

Eine vorab erstellte Bandbreitenrechnung sagte **43 t/s** voraus, kalibriert an
Lagunas gemessenen 25 t/s. Gemessen wurden **2,6 t/s** — Faktor 16 daneben.

Der Fehler war die Grundannahme: Das Modell rechnete, die Generierung sei
bandbreitenlimitiert. Bei 1-Bit-Quants und 6 von 256 zufällig gewählten
Experten stimmt das nicht. **Merke: Bandbreitenrechnungen gelten nur für Q4 und
gröber-aber-nicht-extrem quantisierte Modelle. Bei IQ1/IQ2 dominiert die
Rechenzeit.**

### 9.6 Praxislauf und Qualität

Identischer Prompt („baue ein auto rennspiel und speichere das spiel auf meinem
rechner"):

| Modell | Umfang | lauffähig | Tempo |
|---|---:|---|---:|
| Qwen3.6-27B (Q4, dicht) | mittel | ja | 22,7 t/s |
| Laguna S 2.1 (Q4, MoE) | 692 Zeilen, 3 Dateien | erst nach Einzeiler-Fix (8.2) | 25,0 t/s |
| DeepSeek V4 Flash (IQ1_S) | **111 Zeilen, 1 Datei** | sofort | 2,8 t/s |

Ein 260B-Modell liefert bei offener Aufgabe weniger als ein 27B in Q4 — und
legt weder `requirements.txt` noch README an, sondern schreibt die Hinweise nur
in den Antworttext. **Gemessen wird hier die Quantisierung, nicht das Modell.**

Bemerkenswert: Das kleine, anspruchslose Spiel **lief fehlerfrei**, während
Lagunas ambitioniertes abstürzte. Umfang und Korrektheit sind nicht dasselbe.

### 9.7 Konsequenz für die Aufrüstung

Das dreht die naheliegende Reihenfolge um:

| Maßnahme | Wirkung |
|---|---|
| **3975WX** (32 statt 12 Kerne) | greift genau am Engpass an |
| **RAM auf 128 GB** | ermöglicht IQ4 statt IQ1 — *Qualität*, kein Tempo |
| dritte 5070 Ti | schwächste Option, RAM-Anteil dominiert weiter |

Speicherstand geprüft: **8 × 8 GB, alle acht Kanäle belegt** (Channel A–H,
G.Skill F4-3200C16-8GVKB, konfiguriert auf 3200 MT/s). Es ist **kein Slot
frei** — Aufrüstung geht nur als kompletter Satz von acht. 32-GB-UDIMMs sind
für die Plattform verfügbar, 8×32 GB = 256 GB ist eine gängige Konfiguration.

**Das Modell wurde nach dem Test wieder gelöscht** (77 GB).

## 10. Werkzeug: `~/llm-tools/passt.py`

Prüft, welche GGUF-Quantisierungen eines Modells auf diese Maschine passen:

```bash
python3 ~/llm-tools/passt.py gemma-4-31B            # sucht das GGUF-Repo selbst
python3 ~/llm-tools/passt.py unsloth/Laguna-S-2.1-GGUF -c 131072
```

Es findet das GGUF-Repo, summiert mehrteilige Dateien, liest die Architektur aus
der `config.json` des Basismodells, rechnet den KV-Cache **mit
Sliding-Window** und stellt jedes Quant gegen das Budget (✅ VRAM / ⚠️ hybrid /
❌ zu groß). Hardware über `VRAM_GIB` und `RAM_GIB` anpassbar.

Zwei Fallen, die beim Bau auffielen und im Werkzeug behoben sind:

- **Sliding-Window ignorieren vervierfacht den KV-Cache.** Ohne die Korrektur
  meldete es für Gemma 4 31B 15,0 GiB statt 2,9 GiB — und hätte Q6_K
  fälschlich als „passt nicht" markiert.
- **Dateinamen taugen nicht als Quant-Bezeichner.** Naives Zerlegen erzeugte
  Phantom-Quants wie „it" und „MTP". Jetzt wird auf bekannte Kennungen
  (`Q\d…`, `IQ\d…`, `BF16`, `MXFP4`) geprüft.

**Faustformel ohne Werkzeug:** Parameterzahl × 0,6 GB ≈ Größe in Q4. Grenzen
dieser Maschine: **~27 GiB** komplett im VRAM, **~80 GiB** hybrid.

## 11. Agentische Systeme — Sondierung

Für den geplanten 24/7-Dauerbetrieb mit mehreren Agenten und Übersicht braucht
es drei getrennte Bausteine:

| Baustein | Zweck | Stand |
|---|---|---|
| Modell-Server | rechnet | `llama-server` ✅ |
| Orchestrator | Warteschlange, Agenten, Wiederanlauf | offen |
| Dashboard | Läufe, Schritte, Fehler sichtbar | offen |

**Ein Modell hat kein Dashboard.** Eine GGUF-Datei ist eine Datei mit Zahlen —
keine Oberfläche, kein Prozess. Das gilt für Hermes wie für jedes andere.

Gefunden: **Hermes Agent** (`NousResearch/hermes-agent`, MIT, Python) — ein
Framework, nicht zu verwechseln mit dem gleichnamigen Modell. Es deckt
Dauerbetrieb, Cron, Subagenten und Messenger-Anbindung ab und ist
**modellagnostisch**, spricht also direkt den lokalen `llama-server` an. Ein
Web-Dashboard ist im README nicht dokumentiert; es gibt ein TUI und ein nicht
näher beschriebenes „Hermes Desktop". Die bezahlten Pläne (Nous Portal) sind
für lokalen Betrieb nicht nötig — einzig die Websuche müsste man selbst
nachrüsten.

**Der Engpass ist der Speicher.** Laguna belegt in Q4 fast die gesamte Maschine.
Mehrere Modelle gleichzeitig — ein kleines fürs Routing, ein großes für die
Arbeit — gehen derzeit nicht.

## 12. Nemotron 3 Super 120B — Hybrid-MoE mit nur 8 Attention-Schichten

`NVIDIA-Nemotron-3-Super-120B-A12B-UD-Q4_K_M`, drei Teile, **76,87 GiB**, in
`~/models/nemotron3-120b/`. Erstes Modell dieser Architektur auf der Maschine.

### 12.1 Metadaten — warum der Kontext hier fast nichts kostet

| | |
|---|---|
| Architektur | `nemotron_h_moe` (Hybrid: Mamba2 + Attention + MoE) |
| Blöcke | **88**, davon nur **8 mit Attention** (`head_count_kv = 2`) |
| Rest | Mamba2, `ssm.state_size 128`, `ssm.inner_size 8192`, 8 Gruppen |
| Experten | **512**, davon **22 aktiv**, `expert_ffn 2688`, 1 geteilter |
| Embedding / Vokabular | 4096 / 131072 |
| Kontext laut Datei | **1 048 576** |

Die acht Attention-Schichten mit je zwei KV-Köpfen ergeben
**8 KiB KV je Token** — 2 × 2 Köpfe × 128 × 2 Byte × 8 Schichten:

| Kontext | KV (f16) |
|---|---:|
| 32k | 0,25 GiB |
| 128k | **1 GiB** |
| 262k | 2 GiB |
| 1M | 8 GiB |

Ein klassischer Transformer dieser Größe bräuchte für 128k rund 40 GiB. Der
Kontext ist hier also **nie der Engpass** — der Platz für die Experten ist es.

### 12.2 Offload-Grenze — Bestätigung von 4.4 an einem zweiten Modell

Ohne `-ts` ist bei **`-ncmoe 76`** Schluss, `-ncmoe 74` bricht mit Ladefehler
ab. Die Belegung verrät warum: **6,7 GiB auf Karte 0, 13,9 GiB auf Karte 1**.
Genau das Muster aus 4.4 — der Layer-Split teilt 44/44, die einzigen schweren
Schichten (78–87, Experten im VRAM) fallen alle auf Karte 1.

Je ausgelagerter MoE-Block kostet hier nur **~0,73 GiB**, nicht-Experten-Anteil
über alle 88 Blöcke ~13,4 GiB.

| Aufteilung | tiefstes `-ncmoe` | VRAM Karte 0 / 1 |
|---|---:|---|
| ohne `-ts` | 76 | 6,7 / 13,9 GiB |
| `-ts 21/4` (Bench) | 71 | — |
| `-ts 22/3` (Server, `-c 131072`) | 75 | **12,2 / 10,6 GiB** |

**Neu gegenüber 4.4: der Bench-Kontext ist nicht der Serverkontext.**
`llama-bench` legt nur Prompt + Generierung an (hier 576 Token). KV für 131k
plus Rechenpuffer kosten **~2 GiB extra** — im Server also zwei bis drei
Schichten Reserve gegenüber dem Bench-Optimum einplanen.

### 12.3 Messwerte

Alle mit `-ngl 99`, CUDA-Build `720d7fa40`:

| `-ncmoe` | `-ts` | Threads | Batch | pp | tg |
|---:|---|---:|---:|---:|---:|
| 88 | — | 12 | 128 | 9,52 ᶜ | 11,41 ᶜ |
| 76 | — | 12 | 128 | 38,02 | **17,18** |
| 76 | — | 16 | 128 | 24,73 | 17,03 |
| 76 | — | 24 | 128 | 39,45 | 10,28 |
| 76 | — | 16 | 512 | 133,13 | 17,63 |
| 76 | — | 24 | 512 | **146,60** | 15,50 |
| 71 | 21/4 | 16 | 512 | 65,05 ᶜ | **18,85** |

ᶜ = kalte Messung, siehe 12.4.

Drei Ableitungen:

- **Batchgröße ist der größte Hebel für pp:** 38 → 147 t/s allein durch
  `-p 512` statt `-p 128`. Mehr Token je Expertenladung.
- **16 Threads ist der Kompromiss.** 24 Threads bringen bei pp wenig und kosten
  bei tg ein Achtel — die SMT-Geschwister teilen sich die Rechenwerke.
- **`-ts` zahlt direkt in tg ein:** 17,6 → 18,85 t/s.

Im Serverbetrieb (`-ncmoe 75 -ts 22/3 -c 131072 -b 512 -t 16 --jinja`):
**tg 17,3–18,4 t/s** stabil. Der allererste Prompt lief mit nur 12,5 t/s — auch
hier der Kalt-Effekt.

### 12.4 Der erste Tabelleneintrag ist immer kalt

Vier Läufe hintereinander in dieselbe Falle getappt. `llama-bench` misst die
erste Konfiguration, **während die 77 GB noch in den Page-Cache laufen**:

| gemessen | warm |
|---:|---:|
| 9,52 | ~38 |
| 18,30 | ~38 |
| 22,15 ± 7,14 | ~133 |
| 65,05 ± 58,40 | ~147 |

Erkennungszeichen ist die **Streuung**: ±58 bei einem Mittel von 65 ist keine
Messung, sondern ein Ladevorgang. **Abhilfe: die erste Konfiguration doppelt
angeben** (`-ncmoe 69,69`) und den ersten Wert verwerfen.

### 12.5 `llama-cli` schreibt am Terminal vorbei — zwei Läufe verloren

`common/console.cpp:141`:

```c
tty = fopen("/dev/tty", "w+");
if (tty != nullptr) { out = tty; }
```

Der erzeugte Text geht **direkt an `/dev/tty`**, nicht an stdout. Folge:
`> datei` und `| tee` bleiben bei 0 Byte, obwohl auf dem Schirm alles steht.
Kostete zwei vollständige Generierläufe à ~15 Minuten, weil das Ergebnis nur im
Scrollback stand.

Dasselbe `tcsetattr` sorgt dafür, dass sich `llama-cli` **nach der Generierung
nicht beendet** — es bleibt hängen, bis man Strg+C drückt.

| | |
|---|---|
| Sofortlösung | `--simple-io` — schaltet auf stdout um |
| Dauerlösung | **`llama-server` + `curl` statt `llama-cli`** für alles Skriptartige |

### 12.6 Ohne Chat-Vorlage kein Instruct-Verhalten

`-no-cnv -p "..."` heißt: **kein Chat-Template, kein System-Prompt, reine
Textfortsetzung.** Das Modell sieht den Auftrag nicht als Auftrag, sondern als
Textanfang.

Ergebnis beim Rennspiel-Prompt: 3,6 KB, ~1500 Token, hörte von selbst auf —
weit unter dem Budget von 16384. Für echte Aufträge daher `--jinja` und
`/v1/chat/completions` statt `llama-cli`.

### 12.7 Flaschenhals gemessen: CPU-Lesebandbreite

Messung alle 3 s während der Generierung, CPU-Auslastung aus `/proc/stat`:

| Verdächtiger | Messung | Urteil |
|---|---|---|
| **CPU** | **67–70 %** gesamt | 16 von 24 Threads = 66,7 % → **am Anschlag** |
| GPU 0 | 20 % | langweilt sich |
| GPU 1 | 2–4 % | langweilt sich |
| iowait | **0 %** | Platte spielt keine Rolle |
| RAM | 58 GiB Cache, stabil | kein Nachladen |
| Swap | 2,1 GiB von 8, unberührt | kalte Seiten anderer Programme |

Die 67 % sehen nach Reserve aus, sind aber keine — die restlichen acht Threads
sind SMT-Geschwister derselben Kerne, und die kosten bei tg (12.3).

**Die Bandbreitenrechnung:** 22 aktive Experten ≈ 6,7 GB je Token in Q4, davon
liegt gut ein Viertel im VRAM → **~5 GB durch den RAM je Token**. Bei 17–18 t/s
sind das **~85 GB/s** — die am 25.07. gemessene Lesegrenze der Maschine.

Anders als bei DeepSeek V4 Flash (9.4) ist es hier **nicht** die
Dequantisierung: Q4_K_M ist grob genug, die Bandbreitenrechnung gilt (9.5).

Damit ist 9.7 an einem zweiten, ganz anders gebauten Modell bestätigt. Prognose
für den 3975WX (4 statt 2 Chiplets, ~130–150 statt ~80 GB/s):

| | jetzt | erwartet |
|---|---:|---:|
| tg | 17,5 t/s | ~30 t/s |
| pp | 147 t/s | ~250 t/s |

Reihenfolge der Aufrüstung unverändert: **CPU fürs Tempo, RAM für
Parallelität**, dritte Karte zuletzt.

### 12.8 Swap geprüft

`/proc/swaps`: **`/swap.img`, eine Datei**, 8 GiB, davon 2,1 GiB belegt,
`swappiness 60`. Bei 0 % iowait während der Generierung ist das kein Bremsklotz
— Page-Cache landet ohnehin nie im Swap.

### 12.9 Praxislauf mit Pflichtenheft — neun Fehler, einer davon inhaltlich

Zweiter Anlauf am Rennspiel, diesmal richtig aufgesetzt: `llama-server --jinja`,
`/v1/chat/completions`, System-Prompt („keine Platzhalter, keine TODOs"), neun
nummerierte Anforderungen, Budget 32000 Token.

| | Einzeiler (12.6) | Pflichtenheft |
|---|---:|---:|
| erzeugte Token | ~1500 | **9196** |
| Zeilen | 166 | **555** |
| Ende | von selbst | `finish_reason: stop`, vollständig |
| Dauer | — | 9 min 23 s inkl. Laden |

**Der Umfang stimmt also — die Korrektheit nicht.** Bis das Spiel überhaupt
etwas anzeigte, waren neun Eingriffe nötig:

| # | Fehler | Art | Wirkung |
|---:|---|---|---|
| 1 | `restartRace` statt `restartGame` (2×) | Name | **fatal** — ReferenceError, Skript bricht ab |
| 2 | `ctx.setLineDash([20,10]*scale)` | Typ | **fatal** — Array × Zahl = NaN, TypeError, rAF-Kette reißt |
| 3 | `.hidden` verliert gegen die ID-Regel | CSS-Spezifität | alle drei Bildschirme gleichzeitig sichtbar |
| 4 | `pointer-events:none` auf den Bildschirmen | CSS | alle Knöpfe tot |
| 5 | `startRace()` blendet Startbildschirm nicht aus | Logik | Rennen läuft hinter dem Overlay |
| 6 | `<button …>Restart</div>` | Syntax | falsches Schluss-Tag |
| 7 | `top=0;left=0` | Syntax | ungültiges CSS |
| 8 | `<!DOCTYPE html>` fehlt | Syntax | Quirks-Modus |
| 9 | **`const scale = percent`** | **Rechnung** | **Perspektive invertiert** |

Acht der neun sind **Verdrahtung**: falscher Bezeichner, vergessener
Klassenwechsel, falsches Tag. Solche Fehler meldet der Browser beim ersten
Laden von selbst.

Nur Nummer 9 ist inhaltlich. `percent = n / drawDistance` läuft von 0 (nächstes
Segment) bis 1 (fernstes), wird aber direkt als Größenfaktor benutzt — das
nächste Segment bekommt Breite null, das fernste die volle. Die Straße läuft
nach unten spitz zu und ist am Horizont am breitesten. **Das Modell hat die
Projektion aufgeschrieben, ohne sie einmal gedanklich durchzurechnen.**

Bemerkenswert ist, was *nicht* kaputt war: Streckenerzeugung, Fahrphysik mit
Fliehkraft, Gegnerlogik, Rundenzählung, WebAudio-Motorgeräusch, Touch-Steuerung
— alles vorhanden und plausibel. Es bestätigt 9.6 in schärferer Form:
**Umfang und Korrektheit sind unabhängig voneinander.**

**Die eigentliche Konsequenz** ist keine über das Modell, sondern über das
Verfahren: Fehler 1–8 hätte eine einzige Rückmeldung aus der Browser-Konsole
erledigt, Fehler 9 ein Blick auf einen Screenshot. Was fehlt, ist nicht ein
besseres Modell, sondern **der Rückkanal** — genau der Baustein, der in 11 noch
offen steht. Ein Modell ohne Rückmeldeschleife liefert Text, kein Ergebnis.
